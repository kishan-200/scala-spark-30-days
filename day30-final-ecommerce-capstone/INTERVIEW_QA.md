# Day 30 – Final E-Commerce Capstone
# Interview Questions and Answers

This document contains 20 interview questions and answers based on the Day 30 Final E-Commerce Capstone project.

The answers are written in a simple and natural way so they can be explained confidently during an interview.

---

## Question 1: Can you explain your Day 30 project?

### Answer

My Day 30 project is a final E-Commerce analytics capstone using Apache Spark.

I combined both batch processing and real-time streaming in the project.

For batch processing, I read transaction data, cleaned it, persisted the cleaned data, calculated customer revenue using a Pair RDD, joined it with product information, applied a UDF, performed window analysis and generated a Spark SQL report.

For real-time processing, I used Spark Streaming with a socket. It receives E-Commerce events in 5-second batches and calculates customer revenue and revenue over a 20-second window.

---

## Question 2: Why did you choose E-Commerce for the final project?

### Answer

I chose E-Commerce because it is a practical use case where I can combine many Spark concepts in one project.

There are transactions, customers, products and real-time events.

This allowed me to use RDDs, Pair RDDs, DataFrames, joins, Spark SQL, UDFs, window functions, persistence, partitioning and streaming together instead of creating separate small examples.

---

## Question 3: What is the overall architecture of your project?

### Answer

The project has two main parts: batch processing and real-time streaming.

The batch processing flow is:

CSV Transactions → DataFrame → Data Cleaning → Persist → Pair RDD → Customer Revenue → Product Join → UDF → Window Analysis → Spark SQL → Partitioning

The streaming flow is:

Live E-Commerce Events → Socket → Spark Streaming → 5-Second Batches → Validation → Customer Revenue → 20-Second Window → Real-Time Output

## Question 4: What happens when your batch application starts?

### Answer

First, I create a SparkSession and read the batch transaction CSV as a DataFrame.

Then I clean and validate the transaction data.

I persist the cleaned DataFrame because I reuse it in multiple operations.

After that, I calculate customer revenue using a Pair RDD, load the product reference data, enrich the transactions, apply the UDF, calculate running customer spending using a window and finally generate the Spark SQL report.

---

## Question 5: Why did you use both RDD and DataFrame?

### Answer

I used both because I wanted to demonstrate the different Spark APIs.

I used DataFrames for structured operations such as joins, Spark SQL, window functions and column transformations.

I converted the cleaned DataFrame into an RDD when I wanted to demonstrate Pair RDD processing using `map` and `reduceByKey`.

For a real production application, I would normally prefer DataFrames for most structured processing because Spark can optimize them.

## Question 6: How did you calculate customer revenue?

### Answer

I converted the transaction data into key-value pairs where the customer ID is the key and the transaction amount is the value.

For example:

`(C001, 25000)`

`(C001, 4500)`

`(C002, 24000)`

Then I used `reduceByKey` to add the amounts belonging to the same customer.

So the result gives me the total revenue generated by each customer.

---

## Question 7: Why did you use reduceByKey instead of groupByKey?

### Answer

I used `reduceByKey` because my requirement was to calculate totals.

`reduceByKey` can perform local aggregation before the shuffle. This can reduce the amount of data that needs to move across the network.

With `groupByKey`, Spark first groups all the values belonging to the same key.

So for calculating customer revenue, `reduceByKey` is a better choice.

---

## Question 8: Why did you use persist in your project?

### Answer

I persisted the cleaned transaction dataset because I reused it for different operations.

For example, I used the cleaned data for customer revenue calculation and product enrichment.

Without persistence, Spark may have to recompute the previous transformations whenever the dataset is used again.

Since I reuse the same data, persistence can avoid unnecessary recomputation.

---

## Question 9: Which storage level did you use and why?

### Answer

I used `StorageLevel.MEMORY_ONLY`.

The idea is to keep the persisted data in memory so repeated operations can access it quickly.

For my practice dataset, this was sufficient.

If I had a much larger dataset that could not completely fit into memory, I could use `MEMORY_AND_DISK`.

## Question 10: How did you use the broadcast variable?

### Answer

I had a small product reference dataset containing product IDs and product names.

I converted that small reference data into a Map and created a Spark broadcast variable.

The product reference data is small compared to the transaction data, so broadcasting makes the same lookup information available to the tasks without repeatedly transferring the same data during processing.

---

## Question 11: Why did you use an accumulator?

### Answer

I created a `LongAccumulator` to track invalid E-Commerce records.

An accumulator is useful for counters because Spark tasks execute separately from the driver.

The executor tasks can update the accumulator and the driver can read the accumulated result.

A normal driver-side variable is not suitable for this type of distributed counter.

## Question 12: What UDF did you implement?

### Answer

I created a transaction-value UDF.

It checks the transaction amount and categorizes the transaction as HIGH, MEDIUM or LOW.

The logic is:

- Amount >= 50000 → HIGH
- Amount >= 25000 → MEDIUM
- Otherwise → LOW

I applied the UDF using `withColumn` and created a new transaction value band.

## Question 13: Why did you use a UDF instead of only using Spark built-in functions?

### Answer

For simple operations, I would prefer Spark's built-in functions because Spark can optimize them better.

I used the UDF in this project mainly to demonstrate custom business logic.

If the same requirement could be implemented using Spark's built-in functions, I would normally prefer the built-in functions in a production application.

## Question 14: How did you use window functions?

### Answer

I created a window partitioned by `customer_id` and ordered by `event_time`.

Then I calculated the running customer spending using the sum of transaction amounts over the window.

For example:

- Transaction 1 → 25000
- Transaction 2 → 29500
- Transaction 3 → 41500

This allows me to see how a customer's spending increases over time while still keeping the individual transaction rows.

---

## Question 15: What is the difference between groupBy and a window function?

### Answer

A `groupBy` combines records into groups and normally produces an aggregated result.

A window function keeps the original rows and calculates an additional value based on related rows.

In my project, I wanted to keep every transaction while also showing the customer's running spending.

That's why I used a window function.

## Question 16: How did you use Spark SQL?

### Answer

After creating the enriched transaction DataFrame, I registered it as a temporary view called `ecommerce_transactions`.

Then I used Spark SQL to calculate:

- Number of transactions
- Total quantity
- Total revenue
- Average transaction value

The results were grouped by product and ordered by total revenue.

## Question 17: What happens during a shuffle in your project?

### Answer

A shuffle happens when Spark needs to move data between partitions.

For example, with `reduceByKey`, records having the same customer ID may be present in different partitions.

Spark needs to bring records with the same key together, so data can move between partitions.

Shuffle is more expensive than simple operations like `map` or `filter` because it can involve network and disk operations.

That is why reducing unnecessary shuffles is important for Spark performance.

---

## Question 18: How did you use partitioning?

### Answer

First, I checked the current number of partitions.

Then I repartitioned the DataFrame using the customer ID with `repartition(4, col("customer_id"))`.

The idea is to distribute records based on the customer key.

This can be useful when later operations repeatedly work with customer IDs.

However, repartitioning itself causes a shuffle, so I would only use it when there is a performance benefit.

## Question 19: Explain the streaming part of your project.

### Answer

For the streaming component, I used Spark Streaming with a socket running on port `9999`.

The application receives live E-Commerce events in 5-second batches.

The input format is:

`transaction_id,customer_id,product_id,quantity,amount`

For example:

`S101,C001,P001,1,25000`

I validate the incoming records and calculate customer revenue using `reduceByKey`.

I also calculate total revenue over a 20-second window.

The application continues processing new batches until I stop it.

---

## Question 20: Why did you use a 20-second window with a 5-second sliding interval?

### Answer

I used a 20-second window to calculate revenue from the most recent 20 seconds of events.

The 5-second sliding interval means Spark updates the calculation every 5 seconds.

For example:

- 0–20 seconds → Window 1
- 5–25 seconds → Window 2
- 10–30 seconds → Window 3

This gives a rolling view of E-Commerce revenue instead of waiting for the entire stream to finish.
